## 1. Утверждённые решения

1. Мир v1: **256×256 тайлов = 8×8 чанков по 32×32 тайла**, тайл 32 px. Размер мира 8192×8192 px.
2. Графика: **качественный Pixel Art, вид сверху**, мрачная постапокалиптическая атмосфера. Только бесплатные или самостоятельно созданные ресурсы.
3. Сюжетное задание: **«Восстановить радиостанцию»**.
4. Сохранения: **IndexedDB через idb-keyval**.
5. Стек (из ТЗ): Phaser 3, TypeScript, Vite. Браузерная игра для телефонов и компьютеров.
6. Без сервера и мультиплеера в v1. Архитектура не мешает их добавлению.
7. Без усложнений «на вырост»: зависимости (`idb-keyval`, `simplex-noise`) подключаются в том этапе, где нужны.

### Готовность к расширению карты

- Вся арифметика координат (тайл ↔ чанк ↔ пиксель) собрана в `src/core/coords.ts` и корректно работает с отрицательными значениями.
- Генератор работает по чанкам; у каждого чанка свой seed `hashInts(worldSeed, cx, cy)`, поэтому результат не зависит от порядка генерации.
- Границы мира заданы в одном месте (`WORLD_CHUNKS` в `config.ts` и функции `isTileInWorld` / `isPointInWorld`). Увеличение карты или переход к бесконечному миру сводится к смене этих границ и добавлению загрузки/выгрузки чанков, без переписывания генератора.
- Сохраняются дельты (изменения), а не карта целиком, поэтому размер сохранения не растёт с размером мира.

## 3. Принципы архитектуры

1. **Логика отдельно от отрисовки.** `GameState` состоит из простых сериализуемых данных (числа, строки, объекты, массивы). Phaser только показывает состояние.
2. **Только команды меняют состояние.** Действие игрока оформляется как `Command` (с `playerId` и `tick`), проходит проверку и применяется обработчиком. Такие же команды в будущем можно отправлять на сервер.
3. **Системы общаются через события и состояние**, а не вызывают друг друга. Все события описаны в `core/events.ts`.
4. **Контент в данных.** Предметы, ресурсы, постройки, квесты, биомы лежат в JSON в `src/data/` (с этапа M1).
5. **Детерминизм.** В логике запрещены `Math.random` и `Date.now`; случайность только через `Rng` с seed.
6. **Единый ввод.** `InputManager` выдаёт «намерения», клавиатура и сенсорные кнопки равноправны (с этапа M2).
7. **Единые форматы.** Базовые типы только в `core/types.ts`, правила координат в `core/coords.ts`, форматы данных в `docs/DATA_FORMATS.md`. Системы не заводят собственных вариантов.

### Правила слоёв (проверяются автоматически)

```
scenes / view / ui / input   ──►  systems  ──►  core
   (Phaser, отрисовка)         (чистая логика)   (состояние, события, Rng)
```

- `core/` и `systems/` **не импортируют** Phaser, `scenes/`, `view/`, `ui/`, `input/`.
- В `core/` и `systems/` нет `Math.random` и `Date.now`.
- Во всём проекте нет `eval`, `new Function` и записи пользовательских данных в `innerHTML`.

Эти правила проверяют и ESLint (`eslint.config.js`), и тест `tests/architecture.test.ts`; последний работает даже без запуска линтера.

## 5. Схема взаимодействия модулей

### Поток действия (пример: сбор ресурса, этап M3)

```
Нажата E или кнопка «Действие» на экране
  → InputManager: намерение `interact`
  → GameScene находит ближайший объект
  → commands.dispatch({ type: 'GATHER', playerId, tick, objectId })
  → обработчик: проверки (рядом? запас есть?) → меняет state → предметы в инвентарь
  → bus.emit('resource:gathered', …)
        ├─► ResourceView: анимация, скрыть истощённый узел
        ├─► HUD: обновить счётчики
        ├─► QuestSystem: проверить условие «собрать N»
        └─► SaveSystem: пометить «есть несохранённые изменения»
```

### Матрица связей

| Система                       | Читает             | Выпускает события                        | Слушает события                                    |
| ----------------------------- | ------------------ | ---------------------------------------- | -------------------------------------------------- |
| WorldGenerator / ChunkManager | seed, дельты       | `chunk:loaded`, `chunk:unloaded`         | нет                                                |
| ResourceManager               | чанки              | `resource:gathered`, `resource:depleted` | `chunk:loaded`                                     |
| Inventory                     | описания предметов | `inventory:changed`                      | нет                                                |
| BuildingSystem                | инвентарь, чанки   | `building:placed`, `building:failed`     | `inventory:changed`                                |
| SignalSystem                  | постройки, квест   | `signal:sent`, `signal:received`         | `building:placed`                                  |
| QuestSystem                   | состояние          | `quest:updated`, `quest:completed`       | `resource:gathered`, `building:placed`, `signal:*` |
| SaveSystem                    | всё состояние      | `save:done`, `save:failed`               | события-триггеры автосохранения                    |
| UI и эффекты                  | состояние          | команды (намерения)                      | почти все события                                  |

Уже реализовано в M0: `command:applied`, `command:rejected`, `player:moved`, команда `SET_PLAYER_POSITION`.

## 6. Процедурная генерация мира

### Параметры

Тайл 32 px · чанк 32×32 тайла · мир 8×8 чанков (256×256 тайлов) · старт игрока в центре мира (тайл 128, 128).

### Конвейер генерации чанка (этап M1)

```
текст seed ─ sanitizeSeedText ─ hashString ─► worldSeed (число)
для каждого чанка (cx, cy): chunkSeed = hashInts(worldSeed, cx, cy)
  1. Рельеф: шум высоты и влажности (simplex, по МИРОВЫМ координатам тайла) → тип тайла
  2. Биом: пара «высота/влажность» по таблице biomes.json
  3. Природные объекты: деревья, камни; выборка с минимальным расстоянием
  4. Ресурсные узлы: по resources.json; дальше от старта богаче
  5. Заброшенные здания и точки интереса: «штампы»; обязательная радиовышка
  6. Проходимость: заливка от старта, прорубание проходов к вышке и ресурсам
  7. Безопасная зона (радиус около 12 тайлов): без воды, без POI, с деревьями и камнями
     (приоритет над шагами 1–5)
```

### Гарантии детерминизма

- Источник случайности только `Rng` (mulberry32) и хеши на целых числах (`Math.imul`, побитовые операции).
- Шум считается по мировым координатам, поэтому границы чанков стыкуются без швов.
- Порядок генерации чанков не влияет на результат (у каждого свой `chunkSeed`).
- Алгоритмы `Rng.ts` зафиксированы «золотыми» тестами, сверенными с независимой эталонной реализацией. Менять их нельзя: это сломает все миры и сохранения.
- В M1 добавляется тест: карта по одному seed совпадает при повторной генерации и при другом порядке чанков.

### Данные чанка и объектов

```ts
interface Chunk {
  cx: number;
  cy: number;
  tiles: Uint8Array; // 32×32 тайла, индекс = localTileIndex(lx, ly)
  objects: WorldObject[];
}
interface WorldObject {
  id: string; // `${cx}:${cy}:${index}`, стабильный
  type: string; // ключ из data/*.json
  x: number;
  y: number; // координаты тайла
}
```

Стабильные `id` нужны для сохранений (что собрано, что построено) и для будущего мультиплеера.

## 7. Сохранения (этап M6)

### Что и где хранится

- Хранилище: **IndexedDB через idb-keyval**.
- Ключи: `ls:meta` (список слотов с краткой информацией для меню), `ls:slot:1` … `ls:slot:3` (минимум три слота), `ls:slot:N:prev` (предыдущая успешная запись).
- Формат: `{ version, savedAt, playTimeMs, state, deltas }`. Не карта, а **seed плюс изменения**: собранные ресурсы, постройки, инвентарь, позиция игрока, квест, радиостанция.
- Описание формата и правил миграции: `docs/DATA_FORMATS.md`.

### Когда сохраняем

| Триггер                                                                                             | Поведение                                                             |
| --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| После важных действий (постройка, шаг квеста, отправка сигнала, закрытие инвентаря после изменений) | Автосохранение с задержкой 1–2 с (объединяет серию действий)          |
| Периодически                                                                                        | Каждые ~30 с, если есть несохранённые изменения                       |
| Ручное сохранение                                                                                   | Кнопка в меню паузы, немедленная запись с подтверждением              |
| Уход со страницы                                                                                    | `visibilitychange` (скрыта), `pagehide`, `freeze`: немедленная запись |
| Возврат на страницу                                                                                 | `pageshow`, `visibilitychange` (видима): проверка целостности         |

### Особенности мобильных браузеров

- На iPhone событие закрытия вкладки ненадёжно: приложение может быть выгружено из памяти без `unload`/`beforeunload`. Поэтому **единственным основанием безопасности не служат события закрытия**: данные сохраняются заранее (по действиям и по таймеру), а `visibilitychange`/`pagehide` лишь добавочная страховка.
- Запись начинается сразу при скрытии страницы, но завершение асинхронной записи не гарантировано, поэтому сохранения маленькие (быстрые) и всегда есть предыдущая копия `:prev`.
- При загрузке: проверка схемы → при ошибке автоматический откат на `:prev` → при повторной ошибке понятное сообщение и возможность начать заново (игра не падает).
- Safari может очищать данные сайтов, которыми не пользовались около недели (если сайт не добавлен на экран «Домой»). Меры: запрос `navigator.storage.persist()`, подсказка «Добавить на экран Домой», **экспорт и импорт сохранения файлом** (в M6, если вписывается; иначе в M8). Это поведение браузера нужно проверить на реальном устройстве.
- Защита от подмены: числа проверяются на допустимые границы, неизвестные id предметов отбрасываются.

## 8. Графика и атмосфера

### Стиль

Вид сверху, пиксель-арт, тайл 32×32. Приглушённая «выцветшая» палитра, холодные тени, тёплые акценты света (костёр, лампы, огни радиостанции). Заброшенные здания, заросшие леса, ржавый металл, туман.

### Технические решения

- Phaser настроен на пиксель-арт: `pixelArt: true`, `roundPixels: true`, масштаб камеры **только целыми числами** (2×, 3×, 4× по размеру экрана), чтобы пиксели были чёткими.
- Графика загружается атласами (мало запросов, быстрый старт). Тайлы и спрайты можно заменять без изменения кода.
- До готового арта (M1–M6) используются простые пиксельные заглушки, нарисованные программно; замена на арт не затрагивает логику.
- **Освещение** (M7): тёмный слой с режимом `MULTIPLY` и «вырезанными» источниками света (круги с градиентом) у костра, игрока, ламп. Смена времени суток меняет цвет и силу слоя.
- **Туман** (M7): несколько слоёв полупрозрачных шумовых текстур с медленным параллаксом плюс мягкая виньетка по краям.
- **Эффекты** (M7): частицы (дым, искры, пыль, листья), покачивание растительности, дрожь огня.
- **Качество графики**: «низкое / среднее / высокое». На мобильных устройствах по умолчанию среднее, при просадке FPS автоматически снижается. Эффекты Phaser, работающие только в WebGL, должны иметь запасной вариант для Canvas.
- Бюджет производительности: цель 60 FPS на среднем телефоне (не ниже 30 на слабом), ограничение числа объектов на экране, выгрузка дальних чанков.

### Источники ресурсов и лицензии

Только собственные работы или ресурсы с разрешающими лицензиями (CC0 и аналогичные: например Kenney, OpenGameArt с CC0, itch.io с CC0). Каждый внешний ресурс заносится в реестр `docs/ASSETS.md` с автором, ссылкой и лицензией **до** добавления в проект. Ресурсы с неясной лицензией не используются.

### Сюжетное задание «Восстановить радиостанцию» (черновик для Game Designer)

1. Получить обрывок сообщения и узнать о радиовышке, найти заброшенную вышку (она всегда достижима из стартовой зоны).
2. Собрать детали: металлолом, провод, запчасти для передатчика.
3. Построить радиостанцию на базе.
4. Включить её и отправить первый сигнал.
5. Получить ответ (завязка продолжения).

### Определение «готово» для любой функции

1. Работает на ПК и на телефоне (включая iPhone Safari).
2. Логика покрыта тестами.
3. Нет кнопок-заглушек; если что-то не готово, это подписано и указано в отчёте.
4. Прошлые функции не сломаны.
5. Описана в документации.

## 11. Безопасность

- Данные сохранения проверяются схемой до использования.
- Пользовательский текст (seed, названия) очищается: нормализация Unicode, удаление управляющих символов, ограничение длины (`sanitizeSeedText`). Разметка не интерпретируется.
- Нет `eval`, `new Function`, записи в `innerHTML` (проверяется ESLint и тестом).
- Минимум зависимостей; регулярно `npm audit`.
- Секретов в проекте нет и не будет: игра полностью клиентская, а файлы `.env` исключены через `.gitignore`.
- Файлы проекта не удаляются без разрешения владельца.
- Перед крупными изменениями коммит в git.
