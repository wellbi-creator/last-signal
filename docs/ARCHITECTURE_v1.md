## 1. Архитектура и технический стек

### 1.1 Стек

| Слой      | Выбор                        | Зачем                                        |
| --------- | ---------------------------- | -------------------------------------------- |
| Движок    | Phaser 3                     | Утверждено в ТЗ. Рендер, камера, ввод, сцены |
| Язык      | TypeScript (strict)          | Типизация ловит ошибки до запуска            |
| Сборка    | Vite                         | Быстрый dev-сервер, простая сборка           |
| Тесты     | Vitest                       | Юнит-тесты логики без браузера               |
| Линтер    | ESLint + Prettier            | Единый стиль                                 |
| Хранилище | IndexedDB (через idb-keyval) | Сохранения крупнее лимита localStorage       |
| Шум       | simplex-noise (или свой код) | Рельеф и биомы                               |
| Деплой    | GitHub Pages / Netlify       | Бесплатно                                    |

Все инструменты бесплатные. Зависимости минимальны: phaser, simplex-noise, idb-keyval.

### 1.2 Принципы

1. **Логика отдельно от отрисовки.** Все игровые данные живут в `GameState`, состоящем из простых сериализуемых объектов. Phaser только показывает состояние. Сохранение становится простым, а мультиплеер возможным.
2. **Команды вместо прямых вызовов.** Действие игрока (подобрать, построить, передать сигнал) оформляется как `Command`, проходит валидацию и применяется к состоянию. В будущем те же команды можно отправлять на сервер.
3. **Системы не знают друг о друге.** Общение через `EventBus` и через чтение `GameState`.
4. **Контент в данных.** Предметы, ресурсы, постройки, квесты лежат в JSON, правка контента не требует правки кода.
5. **Детерминизм.** Никакого `Math.random` в игровой логике. Только `Rng` с seed.
6. **Единый ввод.** `InputManager` выдаёт намерения (`move`, `interact`, `toggleInventory`...). Клавиатура и джойстик равноправны.

### 1.3 Задел под мультиплеер

- Состояние сериализуемо, команды явные, у каждой сущности стабильный `id`.
- Симуляция (`systems/`) не импортирует Phaser, поэтому её можно запустить на сервере (Node.js).
- `Command` содержит `playerId` и `tick`, хотя в v1 игрок один.
- Генерация мира детерминирована, клиенту достаточно получить seed.

В v1 ничего из сетевого кода не пишется, только соблюдаются эти правила.

## 3. Система процедурной генерации мира

### 3.1 Общая схема

```
worldSeed (строка/число)
   │  hash
   ▼
numeric seed ──► Rng (mulberry32)
   │
   ├─► шумовые поля (рельеф, влажность, растительность)
   │
   └─► для каждого чанка (cx, cy):
         chunkSeed = hash(worldSeed, cx, cy)
         1. Базовый рельеф  → тип тайла
         2. Биом            → правила размещения
         3. Природные объекты (деревья, камни)
         4. Ресурсные узлы
         5. Заброшенные здания и точки интереса
         6. Проверка проходимости
         7. Безопасная зона (только вокруг старта)
```

### 3.2 Параметры

- Размер тайла: 32 px.
- Размер чанка: 32×32 тайла (1024×1024 px).
- В v1 мир конечный: 8×8 чанков (256×256 тайлов). Генератор работает по чанкам, поэтому увеличение карты или переход к бесконечному миру требует лишь смены границ.
- Старт игрока: центр карты.

### 3.3 Детерминизм

Одинаковый Seed обязан давать одинаковую карту.

- Единственный источник случайности: `Rng`, построенный на целочисленной арифметике.
- Шум создаётся из того же seed. Значения шума считаются по мировым координатам тайла, поэтому границы чанков стыкуются без швов.
- Порядок генерации чанков не влияет на результат: у каждого чанка свой `chunkSeed`.
- Запрещены `Math.random`, `Date.now`, итерация по неупорядоченным структурам в генераторе.
- **Автотест:** сгенерировать карту дважды, сравнить хеши. Сгенерировать чанки в разном порядке, сравнить.

### 3.4 Шаги генерации чанка

1. **Рельеф.** Два шумовых поля (высота, влажность) через simplex в несколько октав. Из них получается тип тайла: вода, песок, трава, лес, камень, болото.
2. **Биомы.** Биом определяется парой «высота / влажность» по таблице `biomes.json`: равнина, лес, скалы, побережье, болото. Биом задаёт плотность деревьев, набор ресурсов и вероятность построек.
3. **Природные объекты.** Деревья и камни ставятся по биомной плотности. Размещение через Poisson-подобную выборку с минимальным расстоянием, чтобы не слипались.
4. **Ресурсные узлы.** Дерево, камень, металлолом, вода, растения. Правила в `resources.json` (биомы, плотность, минимальное расстояние от старта). Дальше от старта ресурсы богаче.
5. **Здания и точки интереса.** Заброшенные дома, склады, вышки. Размещаются «штампами» (прямоугольные шаблоны), только на проходимой местности, без пересечений. Для сюжета генерируется точка `radio_tower` на заданном расстоянии от старта.
6. **Проходимость.** После размещения объектов запрещены тупики и закрытые «карманы» вокруг старта и ключевых точек. Проверка заливкой (flood fill) от старта: радиовышка и минимальный набор ресурсов должны быть достижимы. Если нет, прорубается проход (меняем тип тайла на проходимый).
7. **Безопасная стартовая зона.** Радиус около 12 тайлов от старта: нет воды, нет построек-POI, гарантированно есть деревья и камни рядом. Это правило имеет приоритет над шагами 1–5.

### 3.5 Данные тайла и чанка

```ts
type TileId = 'water' | 'sand' | 'grass' | 'forest' | 'rock' | 'swamp';

interface Chunk {
  cx: number;
  cy: number;
  tiles: Uint8Array; // 32*32 значений TileId
  objects: WorldObject[]; // деревья, камни, узлы ресурсов, здания
}

interface WorldObject {
  id: string; // стабильный: `${cx}:${cy}:${index}`
  type: string; // ключ из resources.json / buildings.json
  x: number;
  y: number; // тайловые координаты
}
```

Стабильные `id` нужны для сохранений (что именно собрано) и для будущего мультиплеера.

### 3.6 ChunkManager

- Держит кэш сгенерированных чанков.
- Отдаёт `ChunkRenderer` те, что попадают в радиус видимости (камера ± 1 чанк).
- Выгружает дальние чанки, чтобы телефон не перегружался.
- Применяет к чанку сохранённые изменения (дельты) сразу после генерации.

### 3.7 Что сохраняется

Не карта целиком, а: `worldSeed`, версия формата, дельты (id собранных ресурсов, построенные объекты), позиция игрока, инвентарь, состояние квеста и радиостанции, время игры.

## 4. Схема взаимодействия модулей

### 4.1 Слои

```
┌────────────────────────────────────────────┐
│ scenes / ui / view   (Phaser, отрисовка)   │
└───────────────▲────────────────────────────┘
                │ читают состояние, слушают события
┌───────────────┴────────────────────────────┐
│ systems  (чистая логика, без Phaser)       │
│ World · Resources · Inventory · Building   │
│ Signal · Quests · Save                     │
└───────────────▲────────────────────────────┘
                │
┌───────────────┴────────────────────────────┐
│ core: GameState · Commands · EventBus · Rng│
└────────────────────────────────────────────┘
```

### 4.2 Поток действия (на примере сбора ресурса)

```
Игрок нажал E / кнопку «Действие»
  → InputManager: намерение `interact`
  → GameScene находит ближайший объект в радиусе
  → Commands.dispatch({ type: 'GATHER', playerId, objectId })
  → ResourceManager: проверка (рядом? узел не пуст?)
  → ResourceManager: уменьшает запас узла, возвращает предметы
  → Inventory.add(item, n)
  → EventBus.emit('resource:gathered', {...})
        ├─► ResourceView: анимация, скрыть истощённый узел
        ├─► HUD / InventoryPanel: обновить счётчики
        ├─► QuestSystem: проверить условие «собрать N»
        └─► SaveSystem: пометить дельту (autosave по таймеру)
```

### 4.3 Матрица связей

| Система                       | Читает                | Генерирует события                       | Слушает события                                    |
| ----------------------------- | --------------------- | ---------------------------------------- | -------------------------------------------------- |
| WorldGenerator / ChunkManager | seed, дельты          | `chunk:loaded`, `chunk:unloaded`         | нет                                                |
| ResourceManager               | чанки, инвентарь      | `resource:gathered`, `resource:depleted` | `chunk:loaded`                                     |
| Inventory                     | предметы (items.json) | `inventory:changed`                      | нет                                                |
| BuildingSystem                | инвентарь, чанки      | `building:placed`, `building:failed`     | `inventory:changed`                                |
| SignalSystem                  | постройки, квест      | `signal:sent`, `signal:received`         | `building:placed`                                  |
| QuestSystem                   | всё состояние         | `quest:updated`, `quest:completed`       | `resource:gathered`, `building:placed`, `signal:*` |
| SaveSystem                    | весь GameState        | `save:done`, `save:failed`               | события-триггеры автосохранения                    |
| UI                            | состояние             | `ui:action` (намерения)                  | почти все события                                  |

### 4.4 Жёсткие правила

- Система не вызывает метод другой системы напрямую, только через команды и события.
- Только `Commands` изменяют `GameState`.
- UI ничего не изменяет сам: он отправляет команды.
- Все события типизированы (`EventMap` в `EventBus.ts`), опечатка в названии не пройдёт компиляцию.

Каждый этап завершается проверкой. К следующему переходим только после закрытия предыдущего. На каждом этапе QA повторяет проверки всех прошлых этапов (регрессия).

| **M5. Радио и квест**       | SignalSystem, радиостанция (постройка), QuestSystem, QuestLog, одно сюжетное задание                     | Квест проходится от начала до конца                                        |
| **M6. Меню и сохранение**   | MainMenu, NewWorldScene, PauseMenu, SaveSystem, схема, миграции, автосохранение                          | После перезагрузки мир, инвентарь, постройки и квест идентичны             |
| **M7. Финал v1**            | Полная QA-проверка, мобильная адаптация, оптимизация, аудит безопасности, документация, отчёт            | Чек-лист из ТЗ (п. 6 и 8) полностью закрыт                                 |

### Предлагаемое сюжетное задание (черновик для Game Designer)

«Восстановить радиостанцию»: найти заброшенную радиовышку, собрать детали (металлолом, провод), построить передатчик на базе, отправить первый сигнал и получить ответ.

### Определение «готово» для любой функции

1. Работает на ПК и телефоне.
2. Покрыта тестами, если это логика.
3. Нет кнопок-заглушек (а если есть, они подписаны «в разработке» и перечислены в отчёте).
4. Прошлые функции не сломаны.
5. Описана в документации.

## 6. Задания специалистам

Lead Developer выполняет M0 и интеграцию, поэтому здесь задания четырёх остальных.

### 6.1 GAME DESIGNER

**Цель:** подготовить игровой контент в виде данных, без кода.

**Задачи:**

1. `biomes.json`: 5 биомов (равнина, лес, скалы, побережье, болото). Для каждого: пороги высоты/влажности, плотность деревьев и камней, набор ресурсов.
2. `resources.json`: 4–5 ресурсов (дерево, камень, металлолом, провод, вода или растения). Запас в узле, время добычи, респаун (да/нет), где встречаются, как меняется количество по мере удаления от старта.
3. `items.json`: предметы инвентаря, размер стека, описание.
4. `buildings.json`: 3 постройки + радиостанция. Размер на сетке, стоимость, назначение.
5. `quests.json`: сюжетное задание «Восстановить радиостанцию»: шаги, условия, текст, награда.
6. Правила сигналов: что значит «первый сигнал», сколько ресурсов нужно, какой ответ приходит.
7. Баланс первых 30 минут игры: сколько ресурсов нужно собрать и сколько времени это займёт.

**Результат:** 5 JSON-файлов + короткий документ `docs/DESIGN_NOTES.md` с логикой баланса.

**Передать Lead Developer:** файлы в `src/data/`. Формат полей согласовать с `DATA_FORMATS.md` до начала работы.

**Срок:** к началу M1 (биомы и ресурсы), остальное к началу M3–M5.

### 6.2 UI/UX DESIGNER

**Цель:** интерфейс, одинаково удобный на телефоне и компьютере.

**Задачи:**

1. Единая тема `theme.ts`: палитра, шрифт, размеры, отступы. Масштабирование по размеру экрана.
2. Главное меню, экран создания мира (поле seed + кнопка «случайный»), меню паузы.
3. HUD: инвентарь-кнопка, подсказка взаимодействия, индикатор квеста.
4. Панель инвентаря: сетка слотов, крупные зоны нажатия.
5. Меню строительства: список построек, стоимость, превью размещения на сетке (зелёный/красный).
6. Журнал заданий.
7. Мобильное управление: виртуальный джойстик слева, кнопки «Действие», «Инвентарь», «Строить» справа, учёт safe-area и пальца на экране.
8. Макеты для двух ориентаций (портрет и ландшафт) и трёх размеров экрана (360×640, 390×844, 1920×1080).
9. Простые анимации: появление панелей, подсветка предмета, отклик нажатия.

**Требования:** минимальная зона нажатия 44×44 px, читаемый текст на малом экране, интерфейс не перекрывает центр игрового поля.

**Результат:** эскизы/описания макетов в `docs/UI_SPEC.md` и затем реализация компонентов в `src/ui/` и `src/input/VirtualJoystick.ts` по согласованным интерфейсам.

**Срок:** макеты к началу M2, компоненты по мере этапов M2–M6.

### 6.3 BACKEND DEVELOPER

**Цель:** надёжное сохранение в v1 и подготовленная основа под сервер.

**Задачи:**

1. `SaveSystem`: запись и чтение в IndexedDB, несколько слотов (минимум 3), автосохранение по таймеру и при выходе.
2. Формат сохранения: `{ version, worldSeed, createdAt, playTime, player, inventory, deltas, buildings, quest, signal }`.
3. `schema.ts`: строгая валидация при загрузке. Повреждённый файл не должен ронять игру: понятная ошибка и возможность начать заново.
4. `migrations.ts`: цепочка миграций между версиями формата, тест на каждую.
5. Защита от подмены: числа в допустимых границах, неизвестные id предметов отбрасываются.
6. Экспорт/импорт сохранения файлом (по желанию в M7).
7. Документ `docs/NETWORK_READINESS.md`: как команды и состояние переносятся на сервер (Node.js, WebSocket), какие места архитектуры за это отвечают. Серверный код в v1 **не пишется**.

**Результат:** `src/systems/save/*`, тесты в `tests/save/`, документация формата в `DATA_FORMATS.md`.

**Срок:** черновик схемы к M3, полная реализация в M6.

### 6.4 QA TESTER

**Цель:** ни одна функция не попадает в «готово» без проверки.

**Задачи:**

1. `docs/TESTING.md`: тест-кейсы на каждый этап M0–M7 (шаги, ожидаемый результат, статус).
2. Автотесты (Vitest):
   - одинаковый seed → одинаковая карта;
   - генерация чанков в разном порядке → тот же результат;
   - стартовая зона безопасна, радиовышка достижима;
   - инвентарь: добавление, удаление, переполнение, стеки;
   - строительство: нехватка ресурсов, занятое место;
   - квест: корректный переход состояний;
   - сохранение/загрузка/миграции/повреждённые данные.
3. Ручные проверки на ПК (Chrome, Firefox) и телефонах (Android Chrome, iOS Safari), обе ориентации.
4. Регрессия: после каждого этапа повторить проверки всех предыдущих.
5. Проверка производительности: FPS на среднем телефоне, рост памяти за 10 минут игры.
6. Проверка безопасности: ввод seed (длинные строки, спецсимволы), порча сохранения, `npm audit`, отсутствие `eval` и `innerHTML` с пользовательскими данными.
7. Список найденных ошибок с шагами воспроизведения и приоритетом.

**Результат:** отчёт по каждому этапу и итоговый QA-отчёт в M7.

**Срок:** тест-кейсы к началу соответствующего этапа, проверка сразу после его завершения.

## 7. Безопасность проекта

- Данные сохранения проверяются схемой перед использованием.
- Пользовательский текст (seed, имя мира) очищается и ограничивается по длине.
- Нет `eval`, `new Function`, вставки пользовательских данных в `innerHTML`.
- Минимум зависимостей, регулярный `npm audit`.
- Файлы проекта не удаляются без разрешения владельца.
- Перед крупными изменениями делается коммит в git.

## 8. Риски

| Риск                              | Решение                                                       |
| --------------------------------- | ------------------------------------------------------------- |
| Просадка FPS на телефонах         | Рендер только видимых чанков, выгрузка дальних, пулы объектов |
| Разная генерация на устройствах   | Целочисленный RNG, без `Math.random`, тест детерминизма       |
| Потеря сохранений при обновлениях | Версия формата + миграции + тесты                             |
| Разрастание сцен в «спагетти»     | Правило импортов, команды и события, код-ревью Lead           |
| Неудобное управление на телефоне  | Ранние макеты, проверка на реальных устройствах с M2          |
